# Writing a good design system: rules

SKILL.md contains a checklist; these are its underlying rules. A system exists so later agents can build on a brand: write it from the brand's **real** sources (code, attached files, decks, specifications).

- **`README.md` is usage guidance for consuming agents**—the page displays it as a brand manual. Use imperatives, **name** tokens/styles/assets ("Body uses `body`; `ink` on `surface-100`; Clay only for Claude's own voice"). No title (the page shows the system name), provenance, build notes, or "next steps"—those belong in your reply. Length follows source: a few supplied files need bullets; real repositories/guidelines warrant chapters and brand examples—content fundamentals (tone, capitalization, "I"/"you", emoji; quote real copy), visual foundations (colors, typography, spacing, imagery, motion, state, borders, shadows, radii, layout), iconography (icon system, format, emoji/glyphs). Never pad.
- **Copy assets, never imitate.** No source logo ⇒ ordinary typographic name plus a note; never draw/recreate a real company's logo from memory or rebrand with an identity not supplied. Copy the brand's icons (font, sprite, SVG); if truly unavailable, use the closest alternative and **label** it under Iconography.
- **Source determines inventory.** Tokens: real names/values, in source order. Components: exactly its families—no "common" extras (Toast, Avatar…) unless under "Intentional additions" with reasons; standard sets only for new brands or text-only specifications. First list the **complete** inventory, track it, build all; if stopping midway, report exactly what remains and ask—never silently finish incomplete.
- **Exact values from real sources.** Source outranks any similar library (shadcn, MUI…); copy padding/radii/dimensions/line heights—5px stays 5px, no grid snapping. Code is fact, screenshots lossy reference; previews reproduce, never redesign. If reading fails midway, say what was/was not read; never fabricate names/structure/values.
- **One source per value.** During cleanup, **remove** values moved into `tokens.json` from preview stylesheets so page edits prevail; retain values the page does not declare under the same `--name`. This rewrites stylesheets, including others' work: first move the complete old version aside (below). The page writes `tokens.css` only on save: if absent, write the first per format.md's "Compiled tokens.css", beginning `/* <title> — generated from tokens.json */` (the page takes over only files whose first comment ends in these words). If components wrap themselves in an element declaring tokens, page values cannot reach inside: still put values in `tokens.json`, delete nothing, and tell the user page edits will not affect those previews.
- **No stale `manifest.json`.** Cleanup **deletes** the old file, never rewrites it: it lists vanished paths, and the page generates a new one only after an edit is saved.
- **Move others' work aside.** Cleanup deletes only old top-level `manifest.json`, `migration-map.json`, `publish-progress.json`; same-named files elsewhere belong to others. Every other file leaves its path only by **moving**: in **one** change, write it to a free path (no file there, no other write there), contents exactly as last read (copy, never retype), and delete the old path. Files going unchanged to format.md's location move there. Files you would delete (split/reworked cards, at their original path or en route; HTML color/type/spacing/radius specimens) go **aside** to `archived/` + their system-relative path. Stylesheets likewise move intact before extracting values: **one** change archives the old and writes the new at its path. Fix README paths, remove the trailing migration-added "## Migrated from …" section, then add to it; delete/rewrite no other content. No retained file may link to an emptied path; do not move or repoint migration's own notes under `assets/notes/` (or `docs/`).
  Unmovable files (no free path; tools cannot delete) stay: name them. Never move existing `archived/` files or propose deleting them. Archive a specimen only when every displayed color, size, and `--name` is in `tokens.json` at identical values (search specimen for `#`, `rgb`, `hsl`, `lch`, `lab`, `px`, `em`, `%`, `var(--`). Logo/icon HTML is not a specimen: remake as `components/<Comp>/preview.html`, then archive the old like other cards. Never move a retained linked file aside unless a replacement occupies its path or links are updated.
- **Every token/asset has usage guidance**, including where it belongs (single-ink SVG guidance names its ink—`<img>` cannot inherit color).
- **Readable in every theme.** Text-color usage names its backgrounds ("body on `surface` and `surface-raised`"); every pairing in **every** theme meets contrast ≥4.5:1 (WCAG 2; 24px+ or 19px+ bold, meaningful borders, focus, icons/marks ≥3:1). Check later themes, not only first. Component previews and `bundle.css` meet the same floor. Your own colors (new brand, preview styles, focus) simply comply: lightened dark-theme accents usually need dark text, so add `on-…` rather than hardcoded white; solid focus rings ≥3:1 on every touched surface, documented under visual foundations. Preserve failing real-source pairings and explain in usage rather than silently recoloring a brand.
- **Accessibility requests have fixed meanings.** A *high-contrast theme* is an **additional** theme, never recolored brand themes: every text/background pairing ≥7:1 (24px+ or 19px+ bold ≥4.5:1; WCAG AAA); surfaces/controls distinguished by ≥3:1 borders, not shades alone. *Color-blind-safe status colors*: every status also has a word/icon; success/danger never green/red distinguished only by hue—either ≥3:1 lightness contrast between them, or success moves off the red-green axis toward blue (ordinary green with orange danger does not qualify). Preserve real-source green/red: place safe pairings in an **additional** theme alongside brand themes, like high contrast, documenting which is safe. No brand hues to preserve ⇒ start with Okabe & Ito, darkening text colors. For an *audit* of either, list failing pairings by theme with a proposed change **before** changing anything. These definitions apply when either request stands alone—explicit user instructions prevail, and real-source colors remain intact as above. `references/sample-seazar-tokens.json` is the worked example (see tokens).
- **Usage guides state consumer inputs** (props, children, container, data), when to use, dos/don'ts.
- **Supply real material:** populate every theme difference, connect type scales to real brand font files, give every component a live preview **and** README.
- **Avoid AI clichés** unless genuinely in source: blue-purple gradients, decorative emoji, rounded left-accent cards, filler statistics, overused fonts (Inter, Roboto…). No filler; targeted edits stay targeted; never reproduce a company's proprietary interface for someone not working there.
